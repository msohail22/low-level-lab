## Question

Consider this line, where `p` may or may not be null:

```cpp
delete p;
```

**True or false:** if `p` is a null pointer, this line is safe and does nothing.

<Choices />

## Explanation

True. The standard says that if the pointer passed to `delete` is null, the
operation has no effect. You do not need to guard it.

So this is redundant:

```cpp
if (p != nullptr) {   // this check buys you nothing
  delete p;
}
```

and this is enough:

```cpp
delete p;
```

The confusion comes from a reasonable generalisation. *Dereferencing* a null pointer
is undefined behaviour, so people assume every operation on null is. `delete` is
carved out as an exception, specifically so that cleanup code does not need null
checks scattered through it.

```
delete p
   │
   ├── p == nullptr ──▶ do nothing, return        ← defined, safe
   │
   ├── p from new ────▶ run destructor, free      ← defined, correct
   │
   ├── p already deleted ──▶ UNDEFINED            ← double free
   │
   └── p from malloc ──────▶ UNDEFINED            ← mismatched allocator
```

Everyday comparison: handing an empty tray back to the kitchen. There is nothing on
it, so nothing happens, and nobody has to check whether it was empty first.

Two things that are *not* safe, and which the diagram shows:

- Deleting the same non-null pointer twice. That is a double free, and it is
  undefined.
- Mixing allocators — `delete` on memory from `malloc`, or `free` on memory from
  `new`.

The usual advice is to avoid the question entirely by using `std::unique_ptr`, which
deletes once, at the right time, and sets itself to null when moved from.
