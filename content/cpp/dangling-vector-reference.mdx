## Description

This compiles with no warnings and often prints the right answer. It is still
broken. Find the defect and give the fix.

```cpp
#include <iostream>
#include <vector>

int main() {
  std::vector<int> values{1, 2, 3};

  int& first = values[0];

  for (int i = 0; i < 100; ++i) {
    values.push_back(i);
  }

  std::cout << first << "\n";   // expecting 1
  return 0;
}
```

<Response />

<Answer>

`first` is a reference into the vector's heap buffer. `push_back` may reallocate
that buffer, which frees the old one. After the first reallocation `first` refers to
freed memory, so reading it is a use-after-free.

The fix is to not hold the reference across the mutation. Either take a copy:

```cpp
int first = values[0];
```

or re-acquire the reference after the loop:

```cpp
for (int i = 0; i < 100; ++i) values.push_back(i);
int& first = values[0];
std::cout << first << "\n";
```

A `std::vector` is a pointer to a heap buffer, plus a size and a capacity. When
`push_back` finds size equal to capacity it allocates a larger buffer, moves every
element across, and frees the old one. Anything pointing into the old buffer — a
reference, a pointer, an iterator — is now dangling. The standard calls this
iterator invalidation.

```
before     buffer A: [ 1 ][ 2 ][ 3 ]        size 3, cap 3
                     ^ first

push_back needs cap 4 → allocate B, move, free A

after      buffer B: [ 1 ][ 2 ][ 3 ][ 0 ]   size 4, cap 6
           buffer A: FREED
                     ^ first ... dangling
```

What makes this dangerous is that it usually appears to work: the freed memory is
often still readable and still holds the old value, so testing prints `1`. It breaks
later, under a different allocator or optimisation level. Build with
`-fsanitize=address` and it fails immediately — that is the tool for this whole
class of defect.

Note that `reserve(103)` before the loop also stops the crash, because no
reallocation happens. That fixes this program, not the habit.

</Answer>
