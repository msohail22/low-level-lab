## Description

C++ has a category of program behaviour the standard refuses to define. If your
program does any of it, the compiler owes you nothing — not a crash, not a value,
not consistency between builds.

Select every option that is undefined behaviour.

<Choices />

<Answer>

The first three are undefined. The last two are defined.

- Out-of-bounds `operator[]` on a vector is undefined. `v.at(10)` throws instead,
  which is defined.
- Signed integer overflow is undefined. Unsigned overflow is not.
- Use-after-free is undefined. The memory often still holds the old value, which is
  what makes it so hard to catch.
- Unsigned overflow wraps modulo 2^N, guaranteed by the standard.
- Relational comparison of pointers into one array is allowed.

Undefined behaviour is not "something unpredictable happens at runtime". It is a
promise you make to the compiler, and the compiler optimises assuming you kept it.

```cpp
int f(int x) {
  return x + 1 > x;   // signed overflow is UB
}
```

The compiler reasons: overflow cannot happen, because the programmer promised it
would not. Therefore `x + 1 > x` is always true. Therefore `return true;`. On
`INT_MAX` the function returns true even though the arithmetic wrapped.

```
what you wrote      what the compiler may emit
──────────────      ──────────────────────────
x + 1 > x           "overflow can't happen" → always true → return 1;
```

The asymmetry between signed and unsigned overflow exists for exactly that reason:
making signed overflow undefined lets the compiler treat `int` as a mathematical
integer.

</Answer>
